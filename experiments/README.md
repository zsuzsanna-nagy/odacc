# ODACC Experiments

This directory contains the experiment runners used for the evaluation of
ODACC, the exact online data-aware object-centric conformance-checking method
described in the accompanying paper.

The runners execute `batch_folder.py` on the benchmark suites, store the raw
outputs of each run, and generate aggregate CSV/JSON files for subsequent
analysis.

## Experiment runners

### `run_validation.py`

Runs the non-Order-Management benchmark suites used for semantic validation and
the smaller scalability experiments.

For these benchmarks, both the proposed symbolic method and the SMT-based
formulation are executed in combined online/offline mode (`mode="both"`).
The resulting runs are used primarily for semantic validation by comparing 
online prefix-alignment results with the corresponding exact offline computation.

The configured suites include:

- comprehensive benchmarks;
- object-attribute benchmarks;
- component scaling;
- deviation scaling;
- extended deviation scaling;
- prefix-length scaling;
- component-merge scaling;
- extended merge scaling;
- simple, medium, and complex guard configurations.

### `run_online_symbolic.py`

Runs the proposed symbolic online method over the full benchmark collection.

This includes the non-Order-Management benchmarks as well as the
Order-Management-derived suites:

- component executions;
- fitting executions;
- controlled control-flow deviations;
- controlled data deviations;
- controlled object-relation deviations;
- two-deviation cases;
- three-deviation cases;
- stress cases with four or five injected deviations.

The runner uses the `symbolic_smt` backend configuration and `mode="online"`.

Per-observation output generated by these runs also contains the information
used for the certification-route analysis.

### `run_online_smt.py`

Runs the exact SMT-based reference formulation over the same online benchmark
collection as `run_online_symbolic.py`.

The runner uses the `smt_smt` backend configuration and `mode="online"`.

The symbolic and SMT runs are kept in separate runners because the SMT
experiments are substantially more computationally demanding and can therefore
be executed or resumed independently.

## Experimental protocol

The paper compares three configurations, all run on the same machine, one
case per process, with a limit of 120 s per update:

| Method | Command | Behaviour at the per-update limit |
|---|---|---|
| SMT reference | `python run_online_smt.py --observation-timeout 120 --online-timeout 0` | the component is given up; its later updates (and those of components merging with it) are skipped, other components continue |
| Exact (proposed, exact mode) | `python run_online_symbolic.py --variant pure-jointlb-lp --observation-timeout 120 --online-timeout 0` | the case stops at the first update over the limit |
| Anytime (proposed, anytime mode) | `python run_online_symbolic.py --variant anytime-smt-jointlb-lp --deadline 20 --smt-after 5 --observation-timeout 60 --online-timeout 0 --on-observation-timeout continue` | each update ends at its 20 s deadline; an update that still exceeds 60 s is recorded, and the case continues |

Each configuration was executed once. Runtimes depend on hardware and solver
versions; run the experiments on an otherwise lightly loaded machine when
reproducing timing results.

## Configuration

The runners use `../cocomot-main` as the CoCoMoT installation; set the
environment variable `ODACC_COCOMOT_ROOT` to use another location.

## Variants of the symbolic method

`run_online_symbolic.py --variant NAME` selects the configuration, e.g.:

- `pure-jointlb-lp`: exact mode with the joint lower bound, LP-guided candidates and the LP
  search heuristic (used in the paper);
- `anytime-smt-jointlb-lp`: anytime mode with the same options, a deadline and the
  SMT strict-improvement check after 5 s (used in the paper);
- `pure`: Levels 1-3 without the LP options;
- `smt-level3`, `anytime-smt`, `jointlb`, ...: further variants for ablation
  (see the `VARIANTS` table in the runner).

Time limits can be set with `--observation-timeout`, `--online-timeout`,
`--deadline` and `--smt-after`; `experiments/rerun_failed.py` reruns only the
cases of a session that did not complete.
